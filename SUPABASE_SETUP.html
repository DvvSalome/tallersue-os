El Taller de los Sueños — Setup de Supabase

Guía paso a paso para dejar corriendo la base de datos, autenticación y la app de Next.js, de cero a funcional.

Dos caminos, mismo resultado:

A. Con Vercel (recomendado): el proyecto ya está enlazado a Vercel y Supabase se provisiona automáticamente desde el Marketplace — un solo comando, sin salir de la terminal.
B. Manual: crear el proyecto directamente en supabase.com y copiar las llaves a mano. Útil si no usas Vercel.

Paso 1Crear el proyecto en Supabase

Camino A — Vercel Marketplace (recomendado)

Si el repo ya está enlazado a un proyecto de Vercel (vercel link), un solo comando crea el proyecto de Supabase, lo conecta y descarga las variables de entorno:

vercel link
vercel integration add supabase --non-interactive

La primera vez te pedirá aceptar los términos de la integración en el navegador (se abre una URL vercel.com/.../accept-terms/supabase). Acepta y vuelve a correr el mismo comando — quedará provisionado y conectado al proyecto. 

vercel env pull .env.local --yes

Camino B — Manual desde el dashboard

  1. Entra a supabase.com → New project.
  2. Elige una organización, nombre (ej. taller-de-los-suenos), contraseña de base de datos y región cercana (ej. us-east-1 o sa-east-1).
  3. Espera ~2 minutos a que aprovisione.
  4. En Project Settings → API, copia:
    • Project URL → NEXT_PUBLIC_SUPABASE_URL
    • anon public key → NEXT_PUBLIC_SUPABASE_ANON_KEY
    • service_role key → SUPABASE_SERVICE_ROLE_KEY (secreta, solo servidor)
  5. En Project Settings → Database, copia la Connection string (modo Session pooler o Direct connection) → POSTGRES_URL_NON_POOLING.

Pega todo eso en un archivo .env.local en la raíz del proyecto (ver Paso 5).

Paso 2Ejecutar el schema SQL

El archivo supabase/schema.sql crea las tablas (comunas, equipos, users, facilitadores, responses, item_catalog, lineas_atencion), las vistas/funciones de análisis, el bucket de Storage para evidencias, y activa Row Level Security en todo.

Opción rápida — script incluido

npm install
npm run db:migrate

Esto corre supabase/schema.sql seguido de supabase/seed.sql contra POSTGRES_URL_NON_POOLING (lee .env.local). Es seguro volver a correrlo: usa if not exists, drop policy if exists y on conflict en todas partes.

Opción manual — SQL Editor de Supabase

  1. Abre tu proyecto en supabase.com → SQL Editor → New query.
  2. Pega el contenido completo de supabase/schema.sql y dale Run.
  3. Repite con supabase/seed.sql.

Paso 3Activar inicio de sesión anónimo (obligatorio)

Sin este paso, "Ya soy participante" no funciona. Los participantes entran con un código de equipo (sin correo, sin contraseña personal) — por dentro usan Supabase Anonymous Sign-ins, que viene desactivado por defecto y solo se activa desde el dashboard (no hay forma de hacerlo por SQL ni por el CLI).
  1. Ve a supabase.com/dashboard/project/<tu-project-ref>/auth/providers (o Authentication → Providers en el menú).
  2. Busca "Allow anonymous sign-ins" y actívalo.
  3. Guarda. No requiere redeploy — el cambio aplica de inmediato.

Para confirmar que quedó activo, prueba desde una terminal con Node:

node -e "
require('@supabase/supabase-js').createClient(
  process.env.NEXT_PUBLIC_SUPABASE_URL,
  process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY
).auth.signInAnonymously().then(({data,error}) => console.log(error?.message ?? 'OK', data?.user?.id));
"

Si imprime OK <uuid>, quedó activo. Si dice Anonymous sign-ins are disabled, revisa el paso anterior.

Paso 4Cargar datos maestros

supabase/seed.sql incluye:

  • Las 16 comunas de Medellín (id 1–16).
  • El catálogo de los 14 ítems (4 bloques) — solo metadatos (clave/tipo/etiqueta); las opciones de cada pregunta viven en src/lib/items.ts en el código, no en la base de datos.
  • Un set de ejemplo de líneas de atención (salud mental, salud sexual, violencia, orientación general), algunas nacionales (comuna_id = NULL) y otras por comuna.
Importante: las líneas de atención de ejemplo son ilustrativas. Reemplázalas por los datos reales de tu equipo antes de un despliegue real — puedes editar supabase/seed.sql y volver a correr npm run db:migrate, o hacer insert/update directamente en el SQL Editor.

Paso 5Crear facilitadores/organizadores

Los facilitadores no se auto-registran desde la app — se crean con un script que usa la service_role key. Cada facilitador tiene un código de grupo y una contraseña compartida (login separado del de participantes, sin cambios respecto al modelo de team-codes). 

# Facilitador con acceso a UNA comuna (ej. comuna 13, San Javier)
npm run facilitador:create -- GRUPO-SANJAVIER "unaClaveSegura123" 13 "Equipo San Javier"

# Facilitador/coordinador con acceso a TODAS las comunas
npm run facilitador:create -- COORDINACION "otraClaveSegura456" all "Coordinación general"

Comparte el código de grupo y la contraseña por un canal seguro (no por la app). El login de facilitador está en /facilitador/login.

Una vez adentro, el facilitador también actúa como organizador: en la pestaña "Códigos de equipo" (/facilitador/dashboard/equipos) crea los códigos que los participantes usan para entrar — no hace falta ningún script para esto, es autoservicio desde el panel.

Paso 6Variables de entorno

Si usaste el Camino A (Vercel), vercel env pull .env.local --yes ya te dejó todo listo. Si fue manual, tu .env.local debe verse así:

NEXT_PUBLIC_SUPABASE_URL=https://xxxxxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...
SUPABASE_SERVICE_ROLE_KEY=eyJ...          # secreta — solo server-side
POSTGRES_URL_NON_POOLING=postgres://postgres.xxxx:PASSWORD@aws-0-xxxx.pooler.supabase.com:5432/postgres?sslmode=require
VariableDónde se usa
NEXT_PUBLIC_SUPABASE_URLCliente browser y servidor
NEXT_PUBLIC_SUPABASE_ANON_KEYCliente browser y servidor (respeta RLS)
SUPABASE_SERVICE_ROLE_KEYSolo scripts/*.mjs y rutas de registro (crear usuarios de Auth) — nunca en el cliente
POSTGRES_URL_NON_POOLINGSolo scripts/run-sql.mjs para correr migraciones
Nunca commitees .env.local. Ya está en .gitignore por defecto (lo agrega create-next-app).

Paso 7Correr la app en local

npm install
npm run db:migrate            # si no lo habías corrido
npm run dev

Abre http://localhost:3000. Deberías poder:

  • Iniciar sesión como facilitador en /facilitador/login con la cuenta creada en el Paso 5, e ir a Códigos de equipo para crear uno.
  • Entrar como participante en /participar con ese código + un apodo (sin correo, sin contraseña personal — falla si el Paso 3 no está activo).
  • Ver la home con las líneas de atención de la comuna del equipo.
  • Responder el formulario de 4 bloques / 14 ítems y descargar el CSV de resultados propios al terminar.

Paso 8Storage para evidencias (fotos)

El ítem 7 (evidencia del bloque 2) sube una foto opcional al bucket privado evidencias, creado automáticamente por schema.sql. Cada archivo se guarda en <user_id>/<archivo> y las políticas de Storage RLS restringen el acceso igual que en la tabla responses: el participante solo ve su propia carpeta, el facilitador ve las carpetas de su comuna. No necesitas configurar nada adicional — si el bucket no aparece en Storage del dashboard, vuelve a correr supabase/schema.sql.

Paso 9Desplegar en Vercel

vercel deploy          # preview
vercel deploy --prod   # producción (pide confirmación explícita)

Como Supabase se conectó vía Marketplace, las variables de entorno ya están sincronizadas con el proyecto de Vercel para Production, Preview y Development — no hay que copiarlas a mano en el dashboard.

Troubleshooting común

Error "self-signed certificate in certificate chain" al correr npm run db:migrate

Ocurre porque sslmode=require en la cadena de conexión de Supabase se interpreta como verify-full en versiones recientes de pg-connection-string, y Node no confía en la CA del pooler por defecto. scripts/run-sql.mjs ya lo maneja quitando sslmode de la URL y pasando ssl: {'{'} rejectUnauthorized: false {'}'} explícitamente al cliente — si escribes tu propio script, haz lo mismo. No uses NODE_TLS_REJECT_UNAUTHORIZED=0 global: apaga la verificación TLS para todo el proceso, no solo esta conexión.

"Ya soy participante" no hace nada / da error al entrar con el código

Casi siempre es el Paso 3 sin activar: revisa con el comando de esa sección. Si ya está activo y el error es "Ese código de equipo no existe o ya no está activo", confirma que el código se creó desde Códigos de equipo en el panel de facilitador y que sigue Activo (no desactivado).

Un participante no puede unirse: "Ese apodo ya está en uso en este equipo"

El apodo es único por equipo (no globalmente) — dos equipos distintos sí pueden reusar el mismo apodo. Si el error aparece con un apodo que parece nuevo, revisa mayúsculas/tildes: la comparación ignora mayúsculas pero no acentos (José y jose chocan; José y Jose no). Nota: si un participante pierde su sesión (borra cookies, cambia de dispositivo) no hay forma de "recuperar" su progreso con el mismo apodo — debe entrar con un apodo distinto (queda como limitación conocida v1).

El facilitador no ve ningún participante

Revisa la comuna_id de su fila en public.facilitadores: si apunta a una comuna sin participantes, la tabla estará vacía (RLS está funcionando correctamente, no es un bug). Usa comuna_id = null para un facilitador con acceso a todas las comunas.

"Sin datos suficientes (mínimo 5 respuestas por comuna)" en Análisis grupal

Es la regla de k-anonimato funcionando: por diseño, ningún agregado se muestra si menos de 5 personas de una comuna respondieron ese ítem. No es un error — espera a tener más respuestas o revisa public.v_group_analysis_closed() / v_group_analysis_texto() en supabase/schema.sql si necesitas ajustar el umbral.

Quiero cambiar el umbral de k-anonimato (o el algoritmo de categorización de texto libre)

El umbral (5) está en las funciones v_group_analysis_closed() y v_group_analysis_texto() en supabase/schema.sql (where total_comuna >= 5). El clasificador de texto libre por palabras clave está en src/lib/categorize.ts — es intencionalmente simple (reglas por palabra clave, no IA) para mantener el stack a solo Next.js + Supabase.

Necesito borrar datos de prueba antes de lanzar de verdad

Los participantes son usuarios anónimos de Supabase Auth (is_anonymous = true, sin email). Para borrar todos: listarlos con supabase.auth.admin.listUsers() filtrando por user.is_anonymous y borrar con supabase.auth.admin.deleteUser(id) — el borrado en cascada limpia automáticamente public.users y public.responses (foreign keys con on delete cascade). Los equipos (public.equipos) no se borran solos: bórralos aparte o desactívalos (activo = false) desde el panel.
